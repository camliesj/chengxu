# 统一档案与工单自动建档设计

## 目标

让 Android 与网页端对客户车辆、保险档案和新增工单后的自动建档使用同一服务端业务规则：任一端创建工单后，均能立即查询到一致的车辆和保险档案；具备网页端同等权限的 Android 用户可以维护相应档案。

## 范围

本功能包包含：

- 新增工单在服务端成功落库时自动创建或更新客户车辆档案；工单含保险到期日时，同时创建或更新保险档案。
- Android 档案入口提供清晰、可横向滚动的“维修历史 / 客户车辆 / 保险档案”三个分区，并显示各自数量。
- Android 客户车辆档案支持查询、详情、新增和编辑；保险档案保留查询、详情、新增、编辑、删除及版本冲突处理。
- Android 创建工单成功后刷新车辆和保险的本地加密缓存。
- 网页端创建工单后刷新档案数据，不再以旧的客户端缓存再次写入自动档案。

本功能包不包含桌面批量导入/导出、车辆档案删除、历史已结算工单编辑或作废工单；它们不影响本次跨端一致性的最小闭环。

## 方案选择

采用服务端统一自动建档，而不是分别由网页和 Android 客户端同步。

创建工单的命令已具备幂等 operationId 和单次 D1 批处理。服务端在同一批处理中写入工单、自动档案、操作完成状态和审计日志。这样重放同一个 operationId 不会重复建立档案，任一端的创建结果一致。

不为本功能新增 D1 表或字段。`customer_vehicles` 与 `insurance_policies` 已以 `(company_id, id)` 为主键存储 JSON 档案；服务端先按企业和车牌读取已有档案，存在则复用其 id，否则由工单 id 派生稳定档案 id。稳定 id 保证首次并发创建同一车牌时不会形成两个自动档案。

## 自动建档规则

1. 创建命令完成字段校验后，以 `company_id + plate` 在客户车辆档案中查找匹配项。
2. 车辆档案存在时保留其 id；不存在时 id 为 `CV-<orderId>`。
3. 车辆的客户、电话、车型、VIN、保险公司、车辆类型来自最新工单；`source` 固定为“维修接待”，`remark` 写入“最近工单：<orderId>”。
4. 工单 `insuranceExpiry` 非空时，以 `company_id + plate` 查找保险档案。存在时保留 id、投保金额和险种；不存在时 id 为 `IP-<orderId>`、金额为 0、险种为“交强险 / 商业险”。客户、电话、车型、VIN、保险公司、到期日来自最新工单。
5. 保险档案自动更新遵守现有版本规则：新档案 `version = 1`，已有档案版本加一并更新 `updated_at`。它属于已幂等的创建命令，不单独要求保险档案 operationId。
6. 工单、车辆、保险（如适用）、工单 operation 和 `create_order` 审计日志必须在同一个 D1 batch 中提交；任一写入失败则不返回创建成功。

## 权限与可见性

- 服务端自动建档随已授权的 `CREATE_ORDER` 命令执行，不要求操作者额外拥有 `customers` 或 `insurance` 页面权限；它不会赋予读取或维护档案的权限。
- `/api/customer-vehicles` 继续使用 `customers` 权限。Android 将该权限映射为查看和维护客户车辆，以匹配网页端当前 GET/POST 行为。
- `/api/insurance-policies` 继续使用 `insurance` 权限。Android 沿用查看和维护保险档案的映射。
- 无页面权限的用户不能进入相应的编辑入口；服务端仍是最终授权边界。

## Android 交互

档案页顶部使用可滚动分段导航，始终完整展示三个类别并附带数量。默认停留在维修历史，但客户车辆和保险档案不会因窄屏被裁切；选择状态在该页会话内保持。

客户车辆列表支持按客户、电话、车牌、车型、VIN 搜索。拥有 `customers` 权限且在线时可新建、编辑；详情页展示所有网页端同等字段。车辆档案不增加删除入口，因为网页端目前也没有该业务动作。

保险档案保持现有的新增、编辑、删除、日期选择器和乐观版本冲突提示。创建工单成功后，Android 并行刷新两个档案仓库；刷新失败不影响已创建工单，并以档案页的缓存状态提示网络错误。

## 网页端适配

网页端的创建路径不再调用旧的 `syncCustomerVehicleFromOrder` 和 `syncInsurancePolicyFromOrder` 写入档案，而是在创建成功后重新拉取两个档案集合。编辑已有工单保持既有的档案同步行为，未纳入本功能包。

## 测试与验收

- Node 合同测试覆盖新工单自动插入车辆、自动插入保险、复用已有档案、无保险到期日不建保险、相同 operationId 重放不重复写入，以及同一 batch 包含全部写入。
- Android JVM 测试覆盖 `customers` 权限的维护映射、车辆新增/编辑 API 映射、创建成功触发档案刷新、档案分区数量和窄屏可滚动导航状态。
- Android 测试代码必须能编译；不启动模拟器。
- 运行 Node 全量测试、网页构建、Android JVM 测试、Android 测试代码编译、lint 和 debug APK 构建；将签名校验通过的 debug APK 复制到 `dist/releases/android/autoservice-android-debug-0.1.0.apk`。

## 数据库结构

- `repair_orders`：既有工单主表，含企业、车辆、保险、状态、金额、版本及结算回执字段。
- `customer_vehicles`：`company_id`、`id`、`record_json`、创建与更新时间，主键为 `(company_id, id)`。
- `insurance_policies`：`company_id`、`id`、`record_json`、`version`、创建与更新时间，主键为 `(company_id, id)`。
- `order_operations`：工单创建命令的幂等记录；本次复用，不新增结构。

本设计不引入 migration。
